## Explainable Recommendation (academic, cite in Chapter 2 / evaluation)

**Tintarev, N. & Masthoff, J. (2012). Evaluating the effectiveness of explanations for recommender systems.** *User Modeling and User-Adapted Interaction, 22*, 399–439.
https://link.springer.com/article/10.1007/s11257-011-9117-5
- Also: Tintarev & Masthoff, "Designing and Evaluating Explanations for Recommender Systems", *Recommender Systems Handbook*, ch. 15: http://www.ag-nbi.de/wp-content/uploads/2015/08/08_TransparentRecommender.pdf
- Concept applied: explanation aims such as transparency (why was this recommended), scrutability (the user can see and correct the reasoning) and effectiveness (it helps the user make a good decision)
- Used in: dropping the "Strong / Good / Fair match" score labels, which say *how much* but not *why*. The "Show where these come from" view names the module (and the "via" skill) behind every matched skill, which supports transparency and scrutability. Also the framework for the user-study questions in evaluation (E2)

**Wachter, S., Mittelstadt, B. & Russell, C. (2017). Counterfactual Explanations Without Opening the Black Box: Automated Decisions and the GDPR.** *Harvard Journal of Law & Technology, 31*(2).
https://arxiv.org/abs/1711.00399 · https://papers.ssrn.com/sol3/papers.cfm?abstract_id=3063289
- Concept applied: a useful explanation tells the person *what would need to change* to get a different outcome (counterfactual / actionable explanation)
- Used in: the "To learn for this job" card with "Learn →" on each gap, and the planned what-if simulator (Phase D)
- Related: Karimi et al., "Algorithmic Recourse: from Counterfactual Explanations to Interventions": https://www.researchgate.net/publication/339323608_Algorithmic_Recourse_from_Counterfactual_Explanations_to_Interventions · Poyiadzi et al., "FACE: Feasible and Actionable Counterfactual Explanations": https://www.researchgate.net/publication/335976114_FACE_Feasible_and_Actionable_Counterfactual_Explanations

**Schellingerhout, R. et al. (2024). Creating Healthy Friction: Determining Stakeholder Requirements of Job Recommendation Explanations.**
https://arxiv.org/html/2409.15971
- Findings used: job seekers preferred **short textual explanations** over numeric visualisations, wanted **explicit references to their own CV / the vacancy**, risked **information overload** (the paper suggests letting users explore details selectively), and wanted explanations as **decision support rather than persuasion**
- Used in: choosing layout B (summary first, few words) with source details available on demand; removing the % score and match labels; no "prove it / build it" buttons on skills the student already has; renaming "Your Bonus Skills: extra skills that strengthen your profile" (vague, persuasive) to "Also mention in your CV (not required, but related)" (a concrete action); removing the raw skill count from the Dashboard (see "Dashboard metric")

**Gutiérrez, F., Charleer, S., De Croon, R., Htun, N. N., Goetschalckx, G. & Verbert, K. (2019). Explaining and exploring job recommendations: a user-driven approach for interacting with knowledge-based job recommender systems.** *Proceedings of the 13th ACM Conference on Recommender Systems (RecSys '19).*
https://dl.acm.org/doi/10.1145/3298689.3347001 · https://www.researchgate.net/publication/335771582_Explaining_and_exploring_job_recommendations_a_user-driven_approach_for_interacting_with_knowledge-based_job_recommender_systems

## Module skill extraction (decided 28 Sep, roadmap A11)

**Decision ("option 2"):** the admin (career office) supplies the **module descriptor** (name + description / learning outcomes); SkillMap **extracts skills from the descriptor text** (IR Objective 1); the admin **reviews** them before students see them. Rejected: admin types skill lists directly (removes Objective 1; universities keep descriptors with learning outcomes, not industry skill lists).

**Internal evidence for the report** (`check_skill_profile.py`, 28 Sep, test student low1, 11 modules):
- The original pipeline sent Groq **only the module name**. Result: 128 rows / 120 unique skills; 9 of 11 modules had exactly 12 skills (the model filling its 5–15 quota)
- Many skills are **not supported by the module description**, e.g. Python Programming (description: variables, control structures, functions, lists, dictionaries, file handling, basic OOP) → NumPy, Pandas, Web scraping, API integration, Unit testing, Version control… (8 of 12 unsupported); Integrated Computer Systems → FPGA design, JTAG, IoT, while **missing** assembly language and computer architecture, which the description names
- Consequences: false matches (e.g. "Spring REST API" credited to a Java module that doesn't teach it, and cited as evidence by "Show where these come from"), false gaps, inflated coverage
- Fix: prompt grounded in name + description, "only skills the description teaches or directly implies, 3–10"; old skills kept in `module_skills_name_only` for an E1 comparison (name-only vs descriptor-grounded)
- Near-duplicates were a small effect (120 → 117 after merging); SBERT ≥ 0.85 produced one wrong merge ("Stakeholder analysis = Stakeholder negotiation") and missed "UML modeling / UML diagramming" → A8 threshold must be chosen on labelled pairs

## Live-job search queries (decided 29 Sep, commit 32b2415)

**Why queries at all:** JSearch (Google for Jobs via RapidAPI) is a search API with no "all ICT jobs" feed, so live jobs can only be collected with search queries. Parameters include `query`, `country`, `date_posted`, `employment_types` (e.g. INTERN, FULLTIME) and `job_requirements` (e.g. `under_3_years_experience`, `no_experience`), see https://github.com/cbeaulieu-gt/career-ops-plugin-jsearch · https://rapidapi.com/letscrape-6bRBa3QguO5/api/jsearch · https://www.openwebninja.com/api/jsearch

**Decision: queries generated from the 2024 market data, not hand-picked** (`scripts/live_jobs/generate_live_queries.py` → `data/live_job_queries.json`, committed as the record)
- Method (report sentence): *"Live-job queries were derived from the 2024 JobStreet ICT postings: each title was reduced to its role (level, location and bracketed details removed; manager and lead titles excluded), the top role of every ICT subcategory was taken, and the remaining budget was filled with the most common roles overall, skipping roles that only add words to a chosen one."* Result: 25 Malaysia + 3 Singapore queries, 53 credits per full fetch
- Why: the hand-written list (32 queries, 29 Sep) couldn't be justified and performed badly. Evidence from the dry run on 29 Sep: "IT graduate programme", "IT project coordinator" and "fresh graduate IT" returned **0 usable ICT jobs**; "junior data analyst" returned a *Lead* Data Scientist, so level words in a query don't filter (the search treats them as keywords)
- Graduate focus comes from ranking (A7), not from query wording. Possible later test: JSearch `job_requirements=under_3_years_experience` on 1–2 queries

**ICT title rule** (`app/services/job_titles.py`, used by the fetcher, the generator and `scripts/tools/remove_non_ict_jobs.py`)
- A job is kept only if its title names an ICT role or technology (software, developer, data, network, IT, backend, Linux, SOC…). Plain "engineer" isn't enough ("Electrical Engineer")
- Evidence (29 Sep dry run on 544 cached results): first version wrongly dropped ~25 real ICT titles (Backend Engineer, Linux Administrator, SOC Analyst…) → technology words added; final version dropped 57, all non-ICT or too vague ("Graduate Trainee", "Internship Program"). On the 138 saved jobs it flagged 5 (marine-engineering graduate programme, FedEx supply-chain trainee, sales coordinator, vague project roles), removed with the tool
- Limitation for the report: a keyword rule, so it can miss unusual ICT titles and let through odd ones (e.g. "HDD Substrate Frontend" engineer)

### A8 outcome and LLM checking (30 Sep)
- **Taxonomy mapping rejected on evidence:** 13.4% of skill uses exact, +2.0% after filler words; 42.8% have nothing close (< 0.6), incl. technical skills (Power BI, Incident Management); SBERT precision per band 17/20 (≥0.95) … 3/20 (0.55–0.65). Evidence: `docs/evidence/a8_taxonomy_summary.txt`, `a8_mapping_sample_labels.csv`
- **Labelling ambiguity:** Claude and the author agreed on 5 of 7 pairs where both were definite; the author marked 12 of 22 "unsure" → rule "merge only if clearly the same; arguable = keep separate"
- **LLM pair checking** (retrieve with SBERT, decide with the LLM): Clavié & Soulié (2023), *LLMs as Batteries-Included Zero-Shot ESCO Skills Matchers* — embedding retrieval + LLM re-ranking improved RP@10 by 22+ points: https://arxiv.org/abs/2307.03539 · Peeters, Steiner & Bizer (2024), *Entity Matching using Large Language Models* — LLMs for deciding whether two records are the same; explicit matching rules in the prompt: https://arxiv.org/abs/2310.11244
- **Why 100% isn't possible:** "same skill" is partly a judgement; people disagree (see above). Precision is measured against a written rule, not a perfect truth
- **First pass result:** blind test, 41/50 "same" correct (82%) → **second, stricter check**: Dhuliawala et al. (2024), *Chain-of-Verification Reduces Hallucination in LLMs*, Findings of ACL: https://aclanthology.org/2024.findings-acl.212/ ; related: Wang et al. (2023), *Self-Consistency*, agreement across answers = higher accuracy: https://arxiv.org/abs/2203.11171
- **Own model?** Not now: training on LLM labels at 82% precision copies their errors. Option B5: fine-tune SBERT on the verified pairs later (ask Mr Au)
- **Judge:** Claude labelled the blind samples (LLM-as-a-judge is accepted when spot-checked by a human: Zheng et al. (2023), *Judging LLM-as-a-Judge*, https://arxiv.org/abs/2306.05685); the author spot-checked
- **Second-pass result (30 Sep):** 349 of 634 kept; **fresh** blind test (50 new pairs, not the 75 used before): 49/50 correct = **98% precision** (with n = 50 the plausible range is roughly 90–99%). Evidence: `docs/evidence/a8_llm_eval_verified.csv`. Cost: lower recall (17 of 25 rejected pairs checked were really the same). Precision is favoured on purpose: a wrong merge makes a student look as if they have a skill they don't (the costly error for gap analysis); a missed merge only leaves two names apart, and SBERT still scores them as related. Precision vs recall trade-off in entity resolution: Tilores, *Entity resolution: precision vs recall*; humans only for the uncertain pairs: Wang et al. (2012), *CrowdER: Crowdsourcing Entity Resolution*, PVLDB 5(11): https://arxiv.org/abs/1208.1927
- **Human overrides:** `data/skill_merge_overrides.json` ("same" / "different"), wins over the LLM; holds the one known error
- **Grouping:** union of merged pairs, but two groups are never joined if any pair between them was judged "different" (stops A~B, B~C chaining A into C)
- **Spellings kept (bug found 30 Sep):** matching must compare every spelling of a merged skill; keeping one spelling lost a real match (Nokia 9/12 → 8/12)

## Performance Optimisation

**Numpy vectorisation — matmul replacing nested Python loops**
- Problem: O(J×G) cosine similarity loop with per-pair norm calls
- Fix: pre-normalise both matrices once, then a single `job_vecs @ grad_vecs.T` matmul (BLAS)
- Result: recommend endpoint 3.1 min → ~377ms
- Applied in: `recommend.py` and `skillgap.py` (shared helpers now in `app/services/skill_profile.py`)

## Reference set of real SkillMap pairs (2B sampling design, researched 1 Oct 23:55)
- **Why not uniform random:** matching pairs are rare among all module × job pairs, so a random sample is mostly obvious non-matches and needs a huge label budget: Marchant & Rubinstein (2017), *In Search of an Entity Resolution OASIS*, PVLDB 10(11) — "extreme class imbalance … can lead to enormous labelling requirements": https://arxiv.org/abs/1703.00617
- **Stratify by a score, then reweight:** Bennett & Carvalho (2010), *Online Stratified Sampling: Evaluating Classifiers at Web-Scale*, CIKM: http://www.cs.cmu.edu/~pbennett/papers/bennett-carvalho-strat-cikm-2010.pdf · Fogliato, Patil, Monfort & Perona (2024), *A Framework for Efficient Model Evaluation through Stratification, Sampling, and Estimation* (ECCV): stratify on model scores; overall accuracy needs Horvitz–Thompson weights because each stratum is sampled at a different rate: https://arxiv.org/html/2406.07320v1
- **Consequence for SkillMap:** bands by SBERT cosine are fine, but (1) report results **per band**, and (2) any overall figure must weight each band by its share of real candidate pairs (store the band sizes). The < 0.55 band is a sanity check only, outside the population the model will be asked about (SBERT stays the candidate filter)
- **Unseen skills only:** pairs whose names occur in the training CSV are excluded (lexical memorisation, Levy et al. 2015, see "Stage 2 training data")
- **Size:** 400 pairs → about ±5 points (95%) on an overall proportion; about ±10 points per band of 100. Enough to compare cosine vs model on the same pairs, not for fine differences
- **Judges (2 Oct):** Claude (in chat), gpt-oss-120b (Groq), **Qwen3.8-27B (Groq)** — Gemini 3.8 Flash was overloaded (503) and 2.5 Flash retired for new users, so Gemini stays on job formatting only. Qwen vs Claude on the first 20 (hard, mostly grey-band) pairs: 12/20; Qwen labels more pairs NARROWER where Claude says RELATED (more lenient)
- **Why a panel of different model families, and why three:** Verga et al. (2024), *Replacing Judges with Juries: Evaluating LLM Generations with a Panel of Diverse Models* — a panel of smaller models from different families beat a single large judge and showed less intra-model bias: https://arxiv.org/abs/2404.18796 · more labellers help with diminishing returns (about four non-expert labels per item matched an expert in Snow, O'Connor, Jurafsky & Ng 2008, *Cheap and Fast — But is it Good?*, EMNLP: https://aclanthology.org/D08-1027/)
- **Not added:** ChatGPT / Copilot in Edge (both OpenAI models → same family as gpt-oss, not independent; chat interfaces don't fix the model version and need 400 pairs copied by hand). Optional 4th judge later: Gemini 3.8 Flash when available (Google), which also allows 3-of-4 majority

## Where BROADER belongs in the 3 classes (researched 2 Oct, after the author's spot-check)
- **The 5-way label was right:** in SKOS (the W3C standard ESCO is built on), broader/narrower are *hierarchical* links and `related` is *associative*; the two are kept apart ("the transitive closure of skos:broader is disjoint from skos:related"): https://www.w3.org/TR/skos-primer/ · https://www.w3.org/TR/skos-reference/ . So judges labelling "project management → IT Project Management" BROADER, not RELATED, follows the standard
- **But BROADER pairs are linked, not unrelated:** relatedness/association covers hierarchical neighbours; similarity is a narrower notion (Hill, Reichart & Korhonen 2015, *SimLex-999*, Computational Linguistics 41(4): associated-but-not-similar pairs are a separate category from unrelated ones): https://arxiv.org/abs/1408.3456 · in recruitment matching, a candidate with only the parent skill is ranked as a partial, "under-qualified" match, not as a non-match (Fazel-Zarandi & Fox 2009, see "Partial credit for near matches")
- **Own evidence:** all 5 of the author's spot-check disagreements were pairs all three judges labelled BROADER (general → specific); she sees them as related. Re-mapping the existing labels (no new labelling): BROADER → NOT gives Fleiss' κ 0.47 and 204 unanimous pairs; **BROADER → RELATED gives κ 0.55 and 230 unanimous** (SATISFIES 79, RELATED 93, NOT 58)
- **Conclusion:** keep the 5 labels as they are (they follow SKOS); change only the 3-class mapping to SATISFIES = SAME + NARROWER · RELATED = RELATED + BROADER · NOT = DIFFERENT. Neither RELATED nor NOT counts for the %, so coverage is unchanged; the gain is the gap list can show a head start ("IT Project Management · you have project management"), and the judges agree more. Decide with v2 (training classes change too)

- **Applied (2 Oct evening):** `merge_reference_labels.py` now maps BROADER → RELATED, the same as v2 training (one rule for training and test). Re-evaluated on the 230 unanimous pairs: cosine macro-F1 0.575 → 0.609 but "has it" precision 0.58 → 0.50 (false "has it" 45 → 61). Not a regression: the newly unanimous pairs are mostly general → specific pairs with similar names, where cosine says "has it" but the student only has the general skill; the old mapping left them out of the unanimous set. v1 (trained with BROADER → NOT) is reported on the old file (`reference_eval_broader_as_not.json`); v2 is compared on the new one

## Abbreviation dictionary (A8 add-on, 2 Oct)
- **Problem (Stage 1 seed-7 run):** one ad lists both "Large Language Models" and "LLMs", "Retrieval-Augmented Generation" and "RAG" → the same requirement counted twice
- **Method:** Schwartz & Hearst (2003), *A Simple Algorithm for Identifying Abbreviation Definitions in Biomedical Text*, Pacific Symposium on Biocomputing — "long form (SHORT)" pairs found by matching the short form's letters backwards through the preceding words, first letter at a word start; reported 96% precision / 82% recall, no training data: https://psb.stanford.edu/psb-online/proceedings/psb03/schwartz.pdf · own addition: try plain word initials first (gets "SQL Server Reporting Services" for SSRS, where the letter walk alone stops at "Server Reporting Services")
- **Sources combined:** (1) definitions written in SkillMap's own job ads; (2) ESCO v1.2.1 alternative labels of digital skills, kept only if the letters account for the whole label (drops loose ones such as "GCC" for "computer programming", "UX" for "create prototype of user experience solutions") and only if a SkillMap skill uses one of the two names
- **Decision stays human** (precision first, like A8): proposals go to `data/abbreviations_review.csv`; only pairs marked `same` are merged (through `skill_merge_overrides.json`, which already wins over the LLM merges). Ambiguous short forms (PM = project / product manager) are marked `different` or left undecided
- Wikidata aliases (CC0) are a possible third source; not used, to keep it simple
- **How large abbreviation dictionaries are built without reviewing every pair (researched 2 Oct 11:25):**
  - ADAM (Zhou, Torvik & Smalheiser 2006, *Bioinformatics* 22(22)): pairs mined automatically from MEDLINE; long-form spelling variants grouped (edit distance ≤ 2; one long form = the other plus extra words); frequency and length-ratio filters; quality checked on random samples of 1,000 pairs: about 2.6% errors (≈ 97% precision): https://academic.oup.com/bioinformatics/article/22/22/2813/197656
  - Allie (Yamamoto et al. 2011, *Database*): spelling variants mapped to one form, the most frequent variant kept as the representative; abbreviations with several meanings kept as separate senses: https://academic.oup.com/database/article/doi/10.1093/database/bar013/463936
  - Lightcast: acronyms and aliases handled automatically, ambiguous ones (AWS = Amazon Web Services or American Welding Society) decided from context, with human taxonomists overseeing: https://kb.lightcast.io/en/articles/7216059-lightcast-skills-taxonomy
  - **Applied to SkillMap:** group spelling variants automatically; auto-accept a short form only if it has a single meaning and at least 2 ads define it (frequency filter); never auto-merge short forms with several meanings (no context at skill-name level, precision first); measure precision with the author's blind spot-check of a random sample of auto-accepted pairs (as A8, ADAM)

## Search vs recommendation: ordering a typed job search (researched 3 Oct)
- **Problem (own evidence):** typing "MES IT Engineer" put that job 9th, because the query only nudged the best-fit ranking (blended into the profile vector at 0.4; exact-title boost +0.2 on the similarity half = +0.1 overall) while skill coverage is half of the score
- **Search and recommendation are different tasks:** LinkedIn's job recommendations rank by member–job fit when there is no query: Kenthapadi, Le & Venkataraman (2017), *Personalized Job Recommendation System at LinkedIn: Practical Challenges and Lessons Learned*, RecSys: http://www-cs-students.stanford.edu/~kngk/papers/personalizedJobRecommendationSystemAtLinkedIn-RecSys2017.pdf
- **Search = retrieve by the query, then re-rank:** LinkedIn's semantic job search retrieves candidates for the query, then a ranker re-orders the top results; the relevance model is trained first and engagement is added on top: Borisyuk et al. (2026), *Semantic Search at LinkedIn*: https://arxiv.org/pdf/2602.07309
- **The query's title is intent:** extracted title entities are used in both candidate selection and ranking: *Powering Job Search at Scale: LLM-Enhanced Query Understanding in Job Matching Systems* (2025): https://arxiv.org/html/2509.09690v1
- **Decision (option A):** with a typed query, order by title-match tier (exact phrase > all words > some words > none), then by the chosen sort (Best fit / Most skills matched) inside a tier; jobs without a title match stay listed below (a typo still returns something). Rejected: a bigger title boost (arbitrary number, no guarantee) and search as a hard filter (empty page on a typo)
- **Fields searched (3 Oct, her request):** title, company and location (`app/services/job_search.py`): phrase in any field > all words across them > some word > none
- **Place / company queries (3 Oct):** LinkedIn's query understanding uses location for filtering in candidate selection and title/company as ranking features (*"certain attributes (e.g., location …) are used for attribute-based filtering during the candidate selection stage"*, https://arxiv.org/html/2509.09690v1). SkillMap: a query that names a company or place only groups the jobs; it is not mixed into the profile vector, so the order inside the group is the student's pure fit
- **Searching by skill (researched 3 Oct, her request after a "python" search put a Python-skill job below the line):** job search engines filter mostly by title, date, level, company and salary; skill filters let applicants and jobs "connect at a very personalized, relevant and deeper level": Muthyala et al. (2017), *Data-driven Job Search Engine Using Skills and Company Attribute Filters*, ICDM workshops: https://arxiv.org/abs/1709.05050 · several fields with different importance = BM25F field weighting (a title match counts more than a match in a less important field): Robertson, Zaragoza & Taylor (2004), *Simple BM25 extension to multiple weighted fields*, CIKM: https://www.researchgate.net/publication/221613382_Simple_BM25_extension_to_multiple_weighted_fields · Indeed supports `title:` / `company:` operators, i.e. a plain keyword searches more than the title: https://www.indeed.com/career-advice/finding-a-job/guide-using-indeed.com-job-search
- **Proposed order:** title phrase > (company / location phrase, or a job skill equal to the query via A8 canonical keys, so "LLM" finds Large Language Models) > all words across title, company, location and skills > some word > none; the matched skill is shown first on the card (explains why the job appeared). Full description text not searched (long, generic words)
- **Jobs that state no level (Best fit penalty, now −0.12 = one step):** Indeed Hiring Lab classifies postings by tasks, not titles: about 46% entry-level, 40% mid-level, 14% senior (US, May 2026; ~95% accuracy on a manual check): https://www.hiringlab.org/2026/07/23/the-labor-market-is-tilting-toward-seniority/ . If an unstated posting followed that mix its expected penalty would be 0.40 × 0.12 + 0.14 × 0.24 ≈ 0.08; since senior roles usually say "Senior" in the title, unstated titles lean further towards entry/mid → about half a step (−0.06) is the evidence-based value. Better but more work: infer the level from the ad's own "N years of experience" text. US data, so state it as an assumption for Malaysia
- **Decision (3 Oct, her choice B):** unstated level = half a step (−0.06); Senior −0.24, Lead −0.36, Manager −0.48 unchanged (`UNSTATED_LEVEL_STEPS = 0.5` in `recommend.py`). Option C (level from "N years of experience" in the ad) kept for later.

## Relation model v2: result and decision (3 Oct)
- **Result on the 230 unanimous reference pairs:** cosine macro-F1 0.609, v2-only 0.441, v1+v2 0.640 ("has it" precision 0.504 / 0.333 / 0.524). v1+v2 vs cosine is **not significant**: McNemar's exact test p = 0.49; paired bootstrap 95% CI of the macro-F1 gain [−0.043, +0.104]
- **Methods:** McNemar's test for two classifiers on the same test items: Dietterich (1998), *Approximate Statistical Tests for Comparing Supervised Classification Learning Algorithms*, Neural Computation 10(7): https://doi.org/10.1162/089976698300017197 · bootstrap confidence intervals for metric differences on a shared test set: Koehn (2004), *Statistical Significance Tests for Machine Translation Evaluation*, EMNLP: https://aclanthology.org/W04-3250/
- **Decision:** keep SBERT cosine (≥ 0.7) + A8 in the app; report the relationship model as a tested-and-rejected design (a negative result is a valid finding when the evaluation is sound). Reasons to state: small in-domain set (482 pairs), out-of-domain v1 data, LLM-judge label noise, and a test set of 230 pairs that can only detect large differences (±~0.07 macro-F1)
- **Why it fails — shortcut learning (measured 3 Oct):** the model calls look-alike pairs "has it" with high confidence (Backlog management → Log management 0.99). In v1 only 4% of NOT pairs share a word but 73% of SATISFIES pairs do, so "shared word = has it" was almost always right in training; in the real test 26% of NOT pairs share a word. Same failure as NLI models that learned the lexical-overlap heuristic: McCoy, Pavlick & Linzen (2019), *Right for the Wrong Reasons: Diagnosing Syntactic Heuristics in Natural Language Inference*, ACL: https://arxiv.org/abs/1902.01007 · general term: Geirhos et al. (2020), *Shortcut learning in deep neural networks*, Nature Machine Intelligence: https://arxiv.org/abs/2004.07780
- **Combination rule:** "has it" only when cosine ≥ 0.7 AND the model says SATISFIES (the two make different errors): 230 pairs false has 61 → 34 (p = 0.054), held-out 162 pairs 37 → 22. Chosen after error analysis, so it needs a fresh blind test before use
- **Next experiments:** re-weight training (repeat v2, drop most v1 easy negatives) and start from an NLI cross-encoder, cross-encoder/nli-MiniLM2-L6-H768 (SNLI + MultiNLI, Apache-2.0): https://huggingface.co/cross-encoder/nli-MiniLM2-L6-H768
- **Result of the fix (runs 3–4, 3 Oct):** starting from the NLI cross-encoder plus re-weighting gives has-precision 0.738 vs cosine 0.504 on the 230 pairs (bootstrap 95% CI of the gain [+0.14, +0.33]) and 0.605 vs 0.448 on the 162 held-out pairs; false "has it" 61 → 17 and 37 → 17; recall falls 0.79 → 0.61. Re-weighting alone (MiniLM) reaches precision 0.587. Interpretation: pre-training on entailment (does A imply B?) gives the model the "look-alike ≠ same meaning" knowledge that 7k skill pairs could not teach; supports transfer from a related task (NLI) rather than more in-domain labels. Confirmed on a fresh blind test set (next lines)
- **Fresh blind test (3 Oct) — report wording: "additional evidence", not "confirms" (87 unanimous pairs; ground truth = three LLM judges + a 30-pair human spot-check):** 150 new pairs, never used for any choice, same three judges (κ 0.52, 3 classes). On the 87 unanimous pairs the NLI + re-weighted model has has-precision 0.609 vs cosine 0.432 (false has 9 vs 21) and macro-F1 0.725 vs 0.574; on 149 majority pairs precision 0.595 vs 0.435. The pass rule (precision above cosine, macro-F1 not worse) was written down before labelling, so the result is not a post-hoc choice. Practice of fixing the analysis before seeing the data: Nosek et al. (2018), *The preregistration revolution*, PNAS 115(11): https://doi.org/10.1073/pnas.1708274114
- **Significance on the blind set:** McNemar exact p = 0.006 (cosine alone right on 9 pairs, model alone on 26); paired bootstrap 95% CI of the macro-F1 gain [+0.03, +0.27] and of the has-precision gain [+0.02, +0.35]; author spot-check of 30 unanimous labels: 30/30 agree
- **Precision of the estimates:** on the blind set the model gave 23 "has it" answers, so its precision 0.609 has a margin of about ±0.20 (95%); halving that margin needs about 4× the pairs (~350 unanimous, ~600 sampled). The direction of the effect is already significant (CIs above zero), so more pairs would narrow the size estimate, not change the decision
- **Cosine is not dropped:** SBERT cosine stays as the candidate finder and in the profile-similarity part of the ranking (IR Objective 2: SBERT + cosine); the model only makes the final "has it / related / not" decision for candidate pairs (pipeline: A8 same skill → SBERT candidates → model)

## OTP, email verification and forgot password (researched 4 Oct 00:30)
- **Login OTP (2FA by email) — not needed:** NIST SP 800-63B-4: "Email SHALL NOT be used for out-of-band authentication" (password-only access to the mailbox, interception, rerouting), so an emailed login code is not a real second factor; but "Confirmation codes that are sent to validate email addresses or are issued as recovery codes ... are not authentication processes and not affected by the above prohibition": https://pages.nist.gov/800-63-4/sp800-63b.html

## Password strength (researched 4 Oct 16:00; decided 15:53 = option A, built 16:15)
- NIST SP 800-63B-4: passwords used as a single factor "a minimum of 15 characters", only "a minimum of eight characters" when part of multi-factor; "permit a maximum password length of at least 64 characters"; "SHALL NOT impose other composition rules (e.g., requiring mixtures of different character types)"; SHALL "compare the prospective secret against a blocklist that contains known commonly used, expected, or compromised passwords", including breach corpuses, dictionary words and "the name of the service, the username, and derivatives"; SHALL NOT force periodic changes; SHALL "offer guidance … to choose a strong password": https://pages.nist.gov/800-63-4/sp800-63b.html
- SkillMap today (checked): backend only checks 8–72 bytes (bcrypt limit); Register's frontend meter REQUIRES a mix (capital / number / symbol) to reach "Medium" = a composition rule NIST forbids; no common-password check; reset and Account settings have no meter → three pages, inconsistent rules
- Three-step reset (4 Oct, her request): code verified first (/auth/verify-reset-code) → 10-minute reset pass (JWT signed with a separate key, so it is refused as a login token; dies when its code is used, expires or a newer code is sent) → new password. Wording: "If <what you typed> has a SkillMap account, we've emailed it a code."
- **Decision A (her choice after my recommendation):** one server-side rule for Register, Account settings and reset (`app/services/password_policy.py`): ≥ 8 characters (deliberately below NIST's 15 for single-factor; stated as a prototype trade-off), no forced character mix, blocklist = SecLists 10k most common passwords (MIT licence, `backend/data/common_passwords.txt`: https://github.com/danielmiessler/SecLists/blob/master/Passwords/Common-Credentials/10k-most-common.txt) + the same word with digits/symbols appended ("password123" was not in the list itself) + "skillmap", username, email name. Meter (`components/PasswordStrength.jsx`) = length guidance only on all three pages (Register's old mix-based "Medium required" removed). **Plus NIST rate limiting:** 10 failed sign-ins for one account → 15-minute pause (429), cleared by a successful sign-in or a password reset; unknown accounts not counted (a pause reveals the account exists; accepted, Register already reveals it)

## Tidy rules for job skills (researched and built 5 Oct, after the first bulk run; all sources opened)
Problem found in the first 40 saved jobs: skills quoting a sentence that never names them, duties saved as required, "any one of" lists saved as separate requirements, one skill under two names. Fixed in code from the stored quote, level and ad text (no Groq), so jobs already saved can be tidied too (`app/services/job_skill_tidy.py`, `scripts/pipeline/tidy_saved_job_skills.py`).
- **Quote must name the skill:** checking that a quote is in the ad does not prove it supports the skill. Liu, Zhang & Liang (2023), *Evaluating Verifiability in Generative Search Engines*, Findings of EMNLP: only "51.5% of generated sentences are fully supported by citations" and "74.5% of citations support their associated sentence": https://aclanthology.org/2023.findings-emnlp.467/ . Kept lenient (any word, initials, name without spaces) so it removes unmentioned skills, not loose wording
- **Duty vs requirement:** UCSB HR, *Job Description Basics*: a duty is "one of the work operations ... in the performance of a function"; qualifications are "the requirements of the position (skills, knowledge & abilities)", tied to the duties: https://www.hr.ucsb.edu/hr-units/compensation/job-description-basics . Fits the UIC split already used for the % (required qualifications = must meet). Rule: under a duties heading, or an unheaded task sentence, "required" becomes "unspecified" unless the sentence has requirement words
- **"e.g." / "such as" lists are examples, so any one meets the requirement:** Merriam-Webster: "E.g. means 'for example' ... coming before an item or list of items": https://www.merriam-webster.com/grammar/ie-vs-eg-abbreviation-meaning-usage-difference · UNC Writing Center: "it's understood that there are more examples than those that you've given": https://writingcenter.unc.edu/tips-and-tools/latin-terms-and-abbreviations/ . "and" lists stay separate (all wanted); a list with items not extracted is not half-grouped
- **Same skill, two names:** merge only when the extra words describe and come at the end ("CI/CD pipelines", "Power BI Desktop"); never a word in front ("Application security", "Computer vision") or a word that names something else ("React Native", "SQL Server"). Same principle as A8: merge only what is clearly the same (precision first)
- **Own evidence (52 real ads, 1,537 skills, every change read by hand):** 4 rejected (e.g. "Redis" quoting the tag line; one arguable: "Debugging" from "investigate bugs"), 89 duty levels changed (e.g. Motorola "Collaborate with front-end team" no longer a required skill), 33 skills grouped (e.g. "one or more programming languages (e.g., Python, Java, C++, C#)"), 11 names merged. An independent review (separate agent) found 5 bugs, all fixed; 46 test cases; a second pass changes nothing
- **Limitation for the report:** rules on wording, so they can miss unusual phrasing (a duty without a heading that starts with a noun; a choice written as "Python/Java"), and an ad's typo can still slip past; precision first throughout (a wrong change is worse than a missed one)

## Scoring formula: IR §2.3.6 vs the build (written 6 Oct for the Mr Au meeting and the report)
- **IR:** S = (1/N) Σ w_k · Sim(u_k, v_k), w_k = 1.0 (A) / 0.8 (B) / 0.6 (C); one score over all N job skills
- **Build, number 1, shown to the student (coverage):** required skills held / required skills. "Held" = same canonical skill (A8) or SBERT cosine ≥ 0.7 (MATCH_THRESHOLD); an either-or group = one requirement; only required skills (fallback: unspecified, then preferred). Grades not used
- **Build, number 2, ranking only (Best fit):** 0.5 · SBERT(profile, job) + 0.5 · Wilson lower bound (95%) of held/required + 0.05 · nice-to-have share − level penalty (entry 0, unstated 0.06, Senior 0.24, Lead 0.36, Manager 0.48); typed search adds a title boost to the SBERT part. Grades enter only through the profile vector (skill repeated ×3 for A/A-, ×2 for B+/B and self-declared, ×1 lower)
- **Worked example:** 9 of 10 required, profile similarity 0.62, 2 of 4 nice-to-have, level unstated → 0.5·0.62 + 0.5·0.60 + 0.05·0.5 − 0.06 = 0.57; card shows "9/10 skills"
- **Why different:** averaging raw cosine gives partial credit to unrelated skills (cosine ~0.2–0.4), so a held / not held line (0.7, step 2 blind tests) instead; grade = strength of evidence, not whether the skill was taught; required vs nice-to-have and either-or groups (IR formula treats every ad word as required); two numbers because "7 of 10" is explainable (Tintarev & Masthoff, transparency); Wilson (Evan Miller) and level penalty keep tiny requirement lists and senior roles from topping a graduate's list. Objective 2 (SBERT + cosine) still met
- **Ask Mr Au:** (1) acceptable to differ from §2.3.6 if explained? (2) grades to count more, e.g. grade-weighted ranking while "X of N" stays?
- **Her decisions 6 Oct:** IR guides but need not be followed exactly, as long as requirements, aims and objectives are met; testing (precision/recall, SUS) belongs to the testing phase; she plans to add MongoDB; programme and intake to be created by the admin together with the module structure; Employer and Admin not built yet, flows must work end to end

## MongoDB for chat history (built 6 Oct; closes the IR §2.3.5 / Sprint 4 gap)
- Why MongoDB for chats and PostgreSQL for the rest: a conversation is one growing list of messages, always read and written whole, per user, with no joins — a document fits; users, modules, grades, jobs and skills are relational (foreign keys, joins in matching) — tables fit. This is the IR's hybrid design, kept small.
- Driver: pymongo (synchronous; our FastAPI endpoints are synchronous `def`, which FastAPI runs in a thread pool). Motor (async) not needed.
- Installed: MongoDB Community Server 9.0.2 (current on 6 Oct) + Compass, local Windows service. The IR says MongoDB 8 (Table 1) / 7 (§2.3.1): report says 9.0.
- Design choices: one document per conversation (`chat_sessions`), index (user_id, updated_at); a chat keeps one mode; max 200 saved messages per chat (the model sees the last 20); another user's id → 404 and a new chat, never written to; MongoDB off → chat still answers, unsaved (2 s server-selection timeout), start-up warning instead of a crash.
- UI: list on the left (her choice A of three mock-ups: left list / History side panel / Recent-chats menu), matching the common pattern of ChatGPT, Claude and Gemini.
- Sources for the SQL + NoSQL split (opened 6 Oct 23:40): MongoDB recommends embedding when the "many" side is viewed in the context of its parent; benefits "better performance for read operations", "retrieve related data in a single database operation", "update related data in a single atomic write operation"; documents must be under 16 MB ([MongoDB Manual, Embedded Data](https://www.mongodb.com/docs/manual/data-modeling/embedding/)): fits one chat = one document, capped at 200 messages. Honest counterpoint for the viva: PostgreSQL's `jsonb` could also hold chats; its docs say JSON and relational "can co-exist and complement each other within the same application" ([PostgreSQL 18, JSON Types](https://www.postgresql.org/docs/current/datatype-json.html)). So MongoDB is a fit + IR-alignment + failure-isolation choice, not a necessity at this scale. **Corrected 7 Oct 00:20 (her challenge, she is right):** failure isolation is one-way only (PostgreSQL down = login fails = whole app down, chat included), so it is a minor bonus, not a reason; "the IR says so" explains but does not justify. For chats alone there is no strong technical case. Fowler: aggregate-oriented stores work "really well when data access is aligned with the aggregates, but what if you want to look at the data in a different way?" ([Fowler, Aggregate Oriented Database](https://martinfowler.com/bliki/AggregateOrientedDatabase.html)); he uses "PolyglotPersistence" for picking a store per data shape ([Fowler, NoSQL Definition](https://martinfowler.com/bliki/NosqlDefinition.html)). ## How to improve the relation model after run 5 (researched 7 Oct 19:15; sources opened)
- **Own error analysis, run 4 on blind v3 (majority labels, p ≥ 0.8):** 44 "has it", 13 wrong, 20 real matches missed. Run 4 is **over-confident both ways** (p 0.99+ or 0.00x) on pairs that share words: false "has it" e.g. cloud-native architecture → Cloud-native infrastructure (1.000), relational database design → Relational SQL (0.999), Network topology identification → Network connectivity (0.999); missed e.g. CI/CD pipelines → DevOps CI/CD (all three judges SAME, p 0.001), UML system design → UML Diagramming (0.000), DevOps practices → DevOps Automation (0.112), database normalisation → Database schemas (0.003). About a third of the misses are pairs the judges split on (e.g. System testing → Testing Strategies), i.e. label noise. Same shortcut problem as before (shared words), not fixed by more targeted pairs (run 5).
- **Soft labels from judge disagreement:** training on the judges' vote distribution instead of only the pairs they agree on. Uma et al. (2021), *Learning from Disagreement: A Survey*, JAIR: with good data "training directly with soft labels achieved better results than training from aggregated or even gold labels"; with limited data, gold + soft together did best ([mlanthology](https://mlanthology.org/jair/2021/uma2021jair-learning)). Wu et al. (2023), *Don't Waste a Single Annotation*: soft labels beat majority-vote hard labels on both datasets, e.g. 68.7 vs 66.9 and 67.7 vs 65.2 macro-F1 ([arXiv 2311.05265](https://arxiv.org/pdf/2311.05265)). SkillMap today keeps only agreed, mirror-consistent pairs (v3: 173 of 400), so soft labels would also use the other ~half of the labelled pairs and tell the model which pairs are genuinely unclear (should reduce p = 0.999 on arguable pairs).
- **Stronger starting model:** cross-encoder/nli-deberta-v3-base: SNLI-test 92.38, MNLI mismatched 90.04 ([model card](https://huggingface.co/cross-encoder/nli-deberta-v3-base/blame/0233b6e1207aa367aa01ac84abd8efecc842f2d1/README.md)); nli-deberta-v3-small: 91.65 / 87.55 ([model card](https://huggingface.co/cross-encoder/nli-deberta-v3-small)). The current MiniLM2-L6-H768's own figures are on SBERT.net, which didn't load (not verified, so no number quoted). Cost: ~3–4× slower per pair; SkillMap caches pair scores, so only the warm-up gets longer.
- **Seed ensemble:** averaging several fine-tuned runs (different seeds) improved BERT on average 5.44% for text classification and 5.50% for NLI (Xu et al. 2020, *Improving BERT Fine-Tuning via Self-Ensemble and Self-Distillation*, [arXiv 2002.10345](https://arxiv.org/pdf/2002.10345)). SkillMap already trains 3 seeds but saves and uses only the first.
- **Plan proposed (run 6):** soft labels (all labelled pairs, both orders, votes → 3-class distribution) + 3-seed average; 6a on MiniLM, 6b on DeBERTa-v3-base, both tested on a fresh blind v4 with the same pass rule; whichever passes goes in, else run 4 stays and the model is frozen. ## Verifying GitHub and LinkedIn accounts (14 Oct 22:30, her idea: students could import someone else's public repo)

- **LinkedIn sign-in can't prove a LinkedIn link.** Sign In with LinkedIn using OpenID Connect returns sub, name, given/family name, picture, locale and (optionally) email; no profile URL or vanity name, and `sub` is pairwise ([Microsoft Learn](https://learn.microsoft.com/en-us/linkedin/consumer/integrations/self-serve/sign-in-with-linkedin-v2)). Decision: LinkedIn and portfolio stay typed (self-declared).
- **GitHub sign-in with no scope** "grants read-only access to public information" ([GitHub: scopes for OAuth apps](https://docs.github.com/en/enterprise-server@3.7/apps/oauth-apps/building-oauth-apps/scopes-for-oauth-apps)): enough to prove the username, nothing private read. Flow per [GitHub: authorizing OAuth apps](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps): `state` against CSRF (ours is a signed, 10-minute token naming the student, with no `sub` so it can't sign in), `prompt=select_account` forces the account picker (several accounts), `allow_signup=false`, `Accept: application/json` on the token exchange; the code expires after 10 minutes.
- **Rate limits:** 60 requests/hour unauthenticated per IP; 5,000/hour for an OAuth app using its client id and secret for public data ([GitHub: REST rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)). Repo checks and language reads use the app's id and secret; GitHub's user token is used once and dropped (not stored).
- **Design (her review):** several accounts per student; a mismatch only warns ("You can still save it; employers will see Not linked to your GitHub"), never blocks; a repo is hers if a connected account owns it or is among its contributors (first 100). Import lists only connected accounts' repos. Sign-in with GitHub for the whole account (option 3) wasn't needed: connecting is enough to prove ownership.
- **OAuth app, not a GitHub App (14 Oct 23:59, her question).** GitHub says GitHub Apps "are generally preferred over OAuth apps" for targeted permissions and short-lived tokens (installation tokens expire after 1 hour; "OAuth tokens remain active until they're revoked") ([GitHub: deciding when to build a GitHub App](https://docs.github.com/en/apps/creating-github-apps/about-creating-github-apps/deciding-when-to-build-a-github-app)). Kept the OAuth app: it asks for no scope (public data only) and SkillMap uses the user token once and drops it, so neither benefit applies. Report line: "An OAuth app with no scope was used; its token is used once and never stored."
- **What employers see when a repo isn't linked (research 14 Oct; decided 15 Oct, her yes).** GitHub itself shows a negative label only on request: by default an unsigned commit gets no verification status ("In all other cases no verification status is displayed"); "Unverified" on unsigned commits appears only if the author turns on vigilant mode, which GitHub advises "only if you sign all of your commits" ([GitHub: displaying verification statuses](https://docs.github.com/en/enterprise-server@3.18/authentication/managing-commit-signature-verification/displaying-verification-statuses-for-all-of-your-commits)). Same reasoning here: "Not linked" can just mean she hasn't connected that account, or the repo has over 100 contributors. Decision: employers see only the positive badge (build_showcase for_employer drops "not_linked"); the student still sees her own "not linked" hint.

## Ranking evaluation method (15 Oct, step 4 research)
- nDCG: Järvelin & Kekäläinen, "Cumulated gain-based evaluation of IR techniques" (ACM TOIS, DOI 10.1145/582415.582418): graded relevance, gain summed down the list, discounted by rank, compared with the ideal ranking; credits systems for putting highly relevant items at the top; supports significance testing.
- LLM relevance judges: Thomas, Spielman, Craswell & Mitra, "Large language models can accurately predict searcher preferences" (SIGIR 2024; arXiv 2309.10621): LLM labels reached "accuracy as good as human labellers" against real searchers' gold labels, cheaper than crowd workers; caveat: "Systematic changes to the prompts make a difference in accuracy, but so too do simple paraphrases" -> fix one prompt before results, several judges, author spot-check.
- Pooling (judge only the union of each system's top-k), as in TREC, keeps judging affordable and fair to both systems.
- Ad length shown to judges (16 Oct, changed BEFORE any score): TREC instructs assessors to "judge a document relevant if any piece of the document is relevant" (https://trec.nist.gov/data/qrels_noneng/index.html), so the judge needs the requirements in view. The first run cut ads at 900 characters to fit the free Groq quota; the author found during the spot-check that many ads spend those on the company introduction (grade then rests on the title). Changed to 3,000 characters, 4 pairs per judge call; 900-character grades kept in docs/evidence/ranking/old_900/, not used. Earlier evaluations unaffected: E1b and the spaCy baseline gave labellers the full ad text, the module checks the full description. Report: say the change, when (before scoring) and why.
